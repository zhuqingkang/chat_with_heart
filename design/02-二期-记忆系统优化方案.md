## 1. 一期落地后的实测诊断

以下问题均已对照一期代码（`memory_store.py` / `distill.py` / `nanocode.py`）逐条核实：

| # | 问题 | 代码位置 | 后果 |
|---|---|---|---|
| D1 | 冲突消解**只在当日文件内**比对 | `memory_store.decide_action()` 默认 `path=day_path()` | 跨天重复记忆无法合并，记忆库随时间劣化 |
| D2 | 相似度用 **Jaccard** | `memory_store.similarity()` | 对长度不等的文本惩罚过重——短条目与长条目永远判不出同源，0.6 阈值形同虚设 |
| D3 | 启动注入**只有 system.md + years.md 前 1200 字** | `memory_store.build_memory_prompt()` | `month.md` 未接入（README 已标"部分完成"）；隔天基本断片 |
| D4 | `messages` 无裁剪；蒸馏时**整份 messages 原样发给 API** | `nanocode.run_turn()` / `distill.distill_messages()` | 长会话必然超模型窗口；蒸馏成本随会话长度线性增长 |
| D5 | 检索为**子串匹配** + 每次全目录 `os.walk` | `memory_store.search_entries()` | 无索引、无排序，量大后召回质量与速度双降 |
| D6 | UPDATE 用**全文 `str.replace`** 定位 | `memory_store.replace_entry()` | 条目文本重复时可能替换错块 |
| D7 | 蒸馏**仅 `/q`、`/c`** 触发 | `nanocode.main()` | 进程崩溃 / 断电丢失整轮记忆 |
| D8 | 好感度与心情取"最后一次写入值" | `memory_store.last_affinity()` / `state.json` | 无平滑，单条记忆即可让情绪跳变 |
| D9 | `recent_entries` 每次请求全目录 walk | `memory_store.recent_entries()` | Web 侧边栏每请求一次全量扫盘 |

**诊断结论**：一期的问题不在"存不下"，而在**"写了用不上"**——
记忆只能被模型主动 `recall` 才生效，而多数时候模型想不到去调它。
因此二期的重心放在读路径（R1–R3）与上下文管理（C1–C3），而非继续加存储层。

## 2. 写路径优化——少记、记对

**W1. 记忆分层 + `facts.md` 事实层** [零依赖]

现状是事件 / 事实 / 流程混在同一种日志条目里，导致"用户偏好零第三方依赖"这类
**稳定事实**会被反复 ADD 成多条。改为给条目加类型字段：

| 类型 | 含义 | 存放位置 | 写入方式 |
|---|---|---|---|
| `episodic` | 具体事件（发生了什么） | L4 日志 | 追加 |
| `semantic` | 稳定事实（用户偏好、身份、项目约定） | `memory/facts.md` | 键值覆写 |
| `procedural` | 流程知识（做某事的正确步骤） | `memory/facts.md` | 键值覆写 |

`facts.md` 用简单的 `## 键` 分块，每块一个事实正文，重复键直接覆写。
`remember` 工具新增 `type` 参数；蒸馏器需先判断条目类型。

> **注意**：`facts.md` 与 L4 日志的冲突消解**必须走同一套相似度函数**，
> 不能各写一套阈值，否则会出现"同一条事实在两处行为不一致"。

**W2. 消解范围外扩 + Dice 系数** [零依赖]

- 范围：比对对象从「当日文件」改为「最近 K 天日志 + `facts.md`」（K 默认 7）。
- 算法：`similarity()` 由 Jaccard 换为 **Dice 系数**
  `2|A∩B| / (|A|+|B|)`——对长度差异不敏感，短条目与大条目同源时仍能命中。
- 兜底：要求公共 bigram 数 ≥ 2，防止短文本偶然高相似被误判为 UPDATE。
- 阈值：沿用 0.60 / 0.90 的形式，但 **Dice 分布与 Jaccard 不同**，
  必须用真实语料重新标定后才算完成 → **[需标定]**。

**W3. 条目 id + 精确 UPDATE** [零依赖]

条目写入时分配 `id`（`<yyyy_mm_dd>-<序号>`，如 `20261029-03`），
`replace_entry` 改为按 id 定位块边界后整块替换，废弃全文 `str.replace`。
同时解决 D6。

**W4. 蒸馏兜底与消息瘦身** [零依赖]

- **触发点扩展**：`atexit.register(safe_distill)` + 每 N 轮（N=8）触发一次增量蒸馏，
  覆盖 D7 的崩溃丢失。
- **消息瘦身**：蒸馏前先剥离 `role: tool` 的长回执，只保留 user/assistant 文本，
  单条超长截断。蒸馏输入体积可降一个数量级，直接解决 D4 的成本问题。
- **增量蒸馏**：每 N 轮只蒸馏「上次蒸馏之后的新增消息」，避免每次全量重写。

## 3. 读路径优化——让记忆真的被用起来

**R1. 召回前置（pre-retrieval）** [零依赖]

每轮用户消息进来后，在调用模型之前先做一次本地检索，
把 top-3 条相关记忆注入本轮上下文的一个 `<related_memories>` 块：

```
<related_memories>
[2026-10-28 21:30] 用户决定项目保持零第三方依赖，倾向用标准库实现
[2026-10-29 10:15] 用户在调试 Windows 沙箱下的 bash 不可用问题
</related_memories>
```

模型不必判断"要不要回忆"，直接带着候选记忆作答；若仍不够，再主动调 `recall` 深挖。
这是 mem0 / Letta 的通行做法，是二期收益最高的一项。

> **注意**：R1 会在**每一轮**都注入内容，是二期最主要的 token 开销来源。
> 必须配分数下限阈值，宁可少召回不可错召回（详见 §11）。

**R2. 倒排索引** [零依赖]

新增 `memory/index.json`：

```json
{
  "docs": {
    "20261029-03": {"file": "2026/10month/2026_10_29.md", "date": "20261029", "layer": "L4"}
  },
  "postings": {"项目": ["20261029-03"], "零依赖": ["20261029-01", "20261029-03"]}
}
```

写入时增量更新（`remember` 成功后同步索引），检索时不再全目录扫盘。
解决 D5 / D9。

**R3. BM25-lite 排序 + 时间衰减** [零依赖]

把子串匹配换成经典 BM25：
`score = Σ IDF(q_i) × tf × (k1+1) / (tf + k1×(1-b+b×len/avglen))`
（k1=1.5, b=0.75），再叠加时间衰减权重 `w_date = 0.9^(距今天数/30)`——
记忆天然是时间局部的，"上个月聊过 XX" 不该和 "今天刚说过" 同权。
纯标准库可实现，约 40 行。

**R4. 启动注入分层预算** [零依赖]

一期 `build_memory_prompt()` 只注入 system.md + years.md 前 1200 字，
既缺 `month.md`，也缺近期记忆。二期改为**带总预算的优先级注入**：

| 优先级 | 内容 | 处理方式 |
|---|---|---|
| 1 | `system.md`（人格） | 全文，不截断 |
| 2 | `facts.md`（稳定事实） | 全文，不截断（内容短） |
| 3 | `years.md`（跨年摘要） | 截断至 1200 字 |
| 4 | `month.md`（当月情绪趋势） | 截断至 600 字 |
| 5 | 最近 3 天日志的**标题 + 情感元数据** | 注入摘要，**不注入正文** |

总预算封顶（建议 2500 字）。第 5 条是关键：
**注入标题和情绪，不注入全文**——细节等模型主动 `recall` 再取，
既保住"最近几天在聊什么"的连续性，又不撑爆 system prompt。解决 D3。

## 4. 上下文管理——省钱、防崩

**C1. 预算裁剪** [零依赖]

维护 `MAX_CONTEXT_TOKENS`（建议按模型窗口的 60% 设）。超预算时：
保留 system + 最近 N 轮原文，中间段压成一条摘要块（递归摘要，
同 Letta 的 recursive summarization / Claude Code 的 compact 思路）。

**C2. tool 结果老化** [零依赖]

`messages` 里 `role: tool` 的内容体积最大且信息价值衰减最快。
只保留最近 K 条（K=10）原文，更早的替换为 `（已省略，共 N 字符）` 占位。

**C3. token 估算** [零依赖]

中文约 1 字 ≈ 0.6~1 token，不能用 `len(text)/4`。
实现 `estimate_tokens()`：中文字符数 + 英文单词数×1.3 + 标点/数字各 0.5，
用于裁剪阈值判定。

## 5. 情感层优化

**E1. 状态指数平滑** [零依赖]

`state.json` 当前是"最后一条写入值"，单条极端事件即可让心情跳变。
改为指数平滑：

```
valence_new = 0.7 × valence_old + 0.3 × valence_event
arousal_new = 0.7 × arousal_old + 0.3 × arousal_event
mood_label   = 由 (valence_new, arousal_new) 落在四象限决定
```

affinity 不参与平滑（累计量，有日志可追溯，保持只累加）。解决 D8。

**E2. `mood_report` 情感时序** [零依赖]

扫近 30 天日志解析 valence/arousal/affinity，输出：
好感度曲线、情绪波动统计、最高/最低点对应事件、情绪标签分布。
作为 `mood_report` 工具暴露给模型。

## 6. 工程健壮性

**X1. 原子写** [零依赖]

`replace_entry` 与 `append_entry` 改为「写临时文件 + `os.replace` 原子替换」，
避免进程在写入中途崩溃导致记忆文件损坏。

**X2. 索引一致性** [零依赖]

`index.json` 与 md 文件可能不一致（如手改 md）。提供
`rebuild_index()` 全量重建入口，并在启动时校验条目数是否匹配，
不匹配则自动重建。

**X3. 检索结果缓存** [零依赖]

`recent_entries`（Web 侧边栏每请求调用）按文件 mtime 做内存缓存，
mtime 未变直接返回，避免每次全目录 walk。

## 7. 落地顺序

按「投入产出比 × 风险」排序，建议分三批：

| 批次 | 项目 | 理由 | 依赖 |
|---|---|---|---|
| **第一批**（核心） | R1 召回前置 + R2 倒排索引 + R3 BM25 排序 | 记忆不召回就是死数据，写再多也没用 | 无 |
| **第一批** | C1 预算裁剪 + C2 tool 结果老化 + C3 token 估算 | 直接降成本、防超窗崩溃 | 无 |
| **第一批** | W2 消解范围外扩 + Dice 系数 | 防记忆库长期劣化；改动 < 30 行 | 无 |
| **第二批** | W1 事实层 facts.md + W3 条目 id | 记忆质量与写入正确性 | 依赖 W3（id 机制） |
| **第二批** | R4 启动注入分层预算 | 补 month.md 缺口 + 控制注入体积 | 依赖第一批 R2/R3 |
| **第二批** | W4 蒸馏兜底 + 消息瘦身 + 增量蒸馏 | 防丢失 + 降成本 | 无 |
| **第三批** | E1 状态平滑 + E2 mood_report | 情感体验一致性 | 依赖 W3 |
| **第三批** | X1/X2/X3 工程健壮性 | 防御性，可择机做 | 无 |

> **里程碑建议**：第一批完成后即为 **v0.9**，核心变化是
> "记忆开始被真正使用"——建议届时做一次 A/B 对照（见 §8），这是二期最值得观测的一跳。

## 8. 验证口径

二期改造必须有可观测指标，否则无法判断"改好了"。建议在第一批落地时
同时加一个 `memory_stats` 统计（纯本地计算，不调 LLM）：

| 指标 | 定义 | 期望 |
|---|---|---|
| 召回命中率 | 用户提问涉及历史信息时，R1 注入的 top-3 是否包含答案 | ≥ 80% |
| 注入 token 占比 | `<related_memories>` 占 system prompt 的比例 | ≤ 5% |
| 上下文 token 峰值 | 单轮请求 messages 的 token 数 | 稳定 < 预算 |
| 记忆库膨胀速率 | 每周新增条目数 / 总条目数 | < 5%（重复写入应被消解） |
| 消解准确率 | UPDATE/NOOP 决策中人工判定正确的比例 | ≥ 90% |
| 蒸馏成功率 | 蒸馏调用成功写入条目数 / 蒸馏触发次数 | ≥ 95% |

消解准确率需要人工抽检——建议每批改造后随机抽 20 条 UPDATE 决策人工核对，
这是唯一能防止"Dice 换掉 Jaccard 后阈值失准"的手段 → **[需人工核验]**。

## 9. 对一期接口的影响（变更清单）

实现二期时，以下一期接口会变化。**一期文档不回改，以本表为准**。

| 位置 | 一期 | 二期 | 对应项 |
|---|---|---|---|
| `memory_store.similarity()` | bigram Jaccard | bigram Dice + 公共数下限 | W2 |

| 新增工具 | — | `mood_report()`、`memory_stats()` | E2 / §8 |
| Web 侧 | `/api/memories` 调 `recent_entries()` | 结构若变，需同步 `web/static/app.js` | X3 |

> **注意**：一期 `memory_store.last_affinity()` 的三级兜底
> （state.json → 历史日志倒序 → 基线 50）是修过 bug 的，
> E1 加平滑时**不得破坏这条兜底链**。

## 10. 向量检索：从「二期」降级为远期

一期原计划二期接 Milvus。综合评估后**降级为远期**，理由：
当前记忆规模（日均个位数条目）远未到需要语义检索的量级，
BM25 + 时间衰减在关键词命中场景下已足够；
而 Milvus 引入部署成本与外部依赖，与本项目「零第三方依赖」的定位冲突。

保留的演进路径（三阶段，按需启动）：

| 阶段 | 方案 | 触发条件 |
|---|---|---|
| 远期 A | sqlite + numpy 余弦相似度（embedding 存 sqlite BLOB） | 条目数 > 5000 或 BM25 召回率明显不足 |
| 远期 B | embedding 与 BM25 **混合检索**（RRF 融合排序） | 远期 A 上线后 |
| 远期 C | Milvus / 向量数据库 | 出现多用户 / 十万级条目 / 需要跨设备共享 |

原 Milvus collection 设计（`memory_chunks`：向量字段 embedding + 标量字段
date/layer/mood_valence/mood_arousal/affinity）保留在案，
迁移到远期 A/C 时可直接复用。

情感时序分析（affinity/mood 按 date 排序 → 好感度曲线、情绪波动报告）
已提前到 §5 E2 实现，不依赖向量检索。

## 11. 注意点清单（实现前必读）

这一节汇总实现时最容易踩的坑，按踩坑概率排序。

1. **不要用 `len(text)/4` 估 token**。中文 1 字 ≈ 0.6~1 token，
   `len/4` 会把中文预算低估约 2 倍，C1/C2 的裁剪阈值全部失准。
2. **Dice 阈值不能直接沿用 0.60 / 0.90**。Jaccard 与 Dice 的分布不同，
   照抄会让 UPDATE 触发率明显偏移。标定方法见 §8。
3. **召回必须有分数下限**。R1 每一轮都注入内容，
   宁可不召回也不要把无关记忆塞进上下文——错召回会直接干扰模型作答。
4. **启动注入只给标题 + 情感，不给正文**。正文留给模型主动 `recall`，
   否则 system prompt 会被撑爆，收益反而为负。
5. **`atexit` 蒸馏要防重入**。`/q` 退出时已经蒸馏过一次，
   `atexit` 会再触发一次 → 必须用"上次蒸馏位置"标志位拦截，
   否则同一段对话被写两遍，记忆库凭空膨胀。
6. **增量蒸馏必须记录 `last_distill_index`**，否则每轮都会重复蒸馏同一段消息。
7. **蒸馏瘦身时不要把 tool 结果全删光**。关键决策常常发生在工具输出里
   （读到的报错、跑出的结果），全删会让蒸馏只剩"用户说了什么"。
   建议保留每条 tool 结果的首尾摘要，而不是无脑截断。
8. **索引与 md 是双写关系**。手改 md、或 md 被外部工具改动后，
   `index.json` 立即失真 → 必须提供 `rebuild_index()` 并在启动时校验。
9. **不要动 affinity 的「只累加」语义**。E1 的平滑只适用于
   valence / arousal / mood_label 三个瞬时量。
   affinity 是累计量、有日志可追溯，平滑会让它与日志正文对不上。
10. **不要破坏 `last_affinity()` 的三级兜底链**
    （state.json → 历史日志倒序 → 基线 50），这是修过 bug 的逻辑。
11. **中文 bigram 会跨标点产生无意义片段**（如"好。下一句"→"好。"）。
    分词前先剥离标点与空白，否则相似度会被无意义 bigram 稀释。
12. **同类事实要收敛到一处**。`facts.md` 与 L4 日志的冲突消解
    必须共用同一个相似度函数与阈值，否则同一事实两处行为不一致。
13. **Web 侧结构变了要同步前端**。`/api/memories` 的返回结构若调整，
    `web/static/app.js` 的渲染逻辑要一并改，否则页面会静默显示异常。
14. **`.gitignore` 的 `/memory/` 规则不作用于 `design/`**。
    设计文档在仓库根 `design/`，能进版本控制；
    记忆数据在 `memory/`，不进任何提交——不要把两者放混。

## 12. 风险与边界

1. **上下文膨胀**：二期必须同时做裁剪（C1/C2/C3），
   否则记忆越强、agent 越笨——这是记忆系统的经典反噬；
2. **索引与源文件漂移**：`index.json` 与 md 是双写关系，
   任何手改 md 都会造成索引失真——靠 X2 的启动校验兜底；
3. **召回噪声**：R1 前置召回可能把不相关记忆塞进上下文，
   反而干扰模型——BM25 分数需设下限阈值，宁可少召回不可错召回；
4. **蒸馏的模型偏差**：情感元数据由 LLM 推断，本身带误差。
   长期累积后可能与用户真实情绪偏离——E1 的平滑只是缓解，
   真正的校正需要用户显式反馈（可作为远期功能）。
